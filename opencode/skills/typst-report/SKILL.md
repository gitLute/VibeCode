# Оформление отчётов в Typst

## Когда применять

Используй этот скилл при запросах на создание или правку отчётов: лабораторная, курсовая или расчётная работа, пояснительная записка (ПЗ), титульный лист, оформление по ГОСТ, файл `.typ` или `report.pdf`.

## Приоритет

Правила этого скилла **обязательны** и имеют приоритет над общими знаниями модели об оформлении отчётов.

## Обязательная проверка окружения (шаг 0)

**ПЕРЕД любой работой с отчётом** убедись, что typst и пакет Ghost установлены и
работоспособны. Проверка обязательна: скомпилированный пакет Ghost может быть
сломан (после `typst update` пропадает локальный файл, на который ссылается
`pages/index.typ`), и тогда **любой** импорт падает — включая импорт стиля. Без
этой проверки поломка обнаруживается только в самом конце, на компиляции
готового отчёта.

```bash
typst --version   # должен быть 0.13 или новее (локальные пакеты @mih4n/ghost)
cd ~/.config/opencode/skills/typst-report/resources
typst compile --root . env-check.typ /tmp/env-check.pdf
```

`resources/env-check.typ` импортирует пакет, применяет `styles.extended` и
вызывает **все** титульные страницы, таблицу, рисунок, управление нумерацией и
приложения. Смысл: поймать не только отсутствие пакета, но и поломку его
внутренних импортов и сигнатур (именно так проявился сломанный 1.0.1).

Требуемое состояние пакета: `~/.local/share/typst/packages/mih4n/ghost/1.0.1/`.

**Трактовка результата:**

| Результат | Что делать |
|---|---|
| Код возврата 0 | Окружение готово, продолжай работу над отчётом. |
| `typst: command not found` | typst не установлен — сообщи пользователю, отчёт собрать нельзя. |
| `is not a valid package name` / `unknown package` | Пакет не установлен или нет нужной версии. |
| `file not found` внутри `@mih4n/ghost` | Пакет установлен, но СЛОМАН: его индексы ссылаются на удалённые файлы. Верни в `pages/index.typ` и `styles/index.typ` строки импорта несуществующих файлов. |
| `unexpected argument: <имя>` / `unknown variable: <имя>` в `pages/*.typ` | Расхождение сигнатуры функции пакета с ожидаемой: параметр удалён из объявления, но используется в теле. Верни параметр. |

При поломке пакета НЕ переписывай отчёт под сломанный пакет и не подменяй его
другим пакетом ГОСТ: почини пакет (с бекапом изменяемых файлов) либо сообщи
пользователю. Известные правки пакета 1.0.1 перечислены в
`resources/formatting-rules/01-import-style.md`.

## Обязательное чтение

**ПЕРЕД генерацией или изменением любого отчёта прочитай:**

1. `resources/formatting-rules/README.md` — правила оформления всех блоков:
   карта «блок → файл правил», принципы работы стиля, общие требования.
   Это **источник истины по оформлению**.
2. Каталог с готовыми отчётами для своего типа работы (см. «Эталоны») — как
   пример структуры и содержания реально сданной работы. Читай `.typ`-файлы
   из `resources/lab-style/` (лабораторная, расчётная) или `resources/curse-style/`
   (пояснительная записка).

При работе с конкретным блоком дополнительно прочитай его файл правил
(карта в README, файлы `01`-`14`).

## Эталоны

| Тип работы | Каталог с готовыми отчётами | Титул |
|---|---|---|
| Лабораторная, курсовая, расчётная (отчёт) | `resources/lab-style/` | `pages.title` |
| Пояснительная записка (ПЗ) | `resources/curse-style/` | `pages.curse-title` |

Эталоны перерабатываются в **реальные реализации работ, проверенные преподавателем**,
и потому могут быть временно неверны или некомпилируемы. Из этого следует:

- источник истины по оформлению — каталог `resources/formatting-rules/`
  (начинай с `README.md`);
- эталон — образец структуры и содержания, а не обязательный к дословному
  копированию синтаксис;
- если эталон не компилируется или противоречит правилам — следуй правилам
  `formatting-rules/` и сообщи пользователю о расхождении;
- файл-заглушка `// Не реализован. заглушка.` — это НЕ эталон: примеров в
  каталоге пока нет, работай только по правилам `formatting-rules/`.

Стиль у обоих эталонов один: `styles.extended` (подробности — в
`formatting-rules/01-import-style.md`).

## Алгоритм

0. **Проверь окружение** (см. «Обязательная проверка окружения»): `typst
   --version` и компиляция `resources/env-check.typ`. Не начинай писать отчёт,
   пока проверка не прошла.
1. Прочитай `resources/formatting-rules/README.md` (обязательно) и примеры
   из каталога своего типа работы (`lab-style` или `curse-style`).
2. При необходимости прочитай файлы правил нужных блоков (карта — в README).
3. Создай файл отчёта в `typst/report.typ` (структура проекта — в
   скилле `project-structure`).
4. Убедись, что все изображения, на которые ссылается отчёт, существуют
   (см. «Плейсхолдеры изображений»).
5. Скомпилируй отчёт:

```bash
typst compile --root "$(pwd)" typst/report.typ report.pdf
```

6. При ошибках компиляции исправь и перекомпилируй до чистой сборки.

## Перекомпиляция эталонов (если эталон менялся)

Собираются все `.typ` из обоих каталогов с примерами:

```bash
cd ~/.config/opencode/skills/typst-report/resources
for d in lab-style curse-style; do
  for f in "$d"/*.typ; do
    typst compile --root . "$f" "${f%.typ}.pdf"
  done
done
```

## Плейсхолдеры изображений

В эталонах рисунки задаются `#picture(image("placeholder.jpg", ...))`. Если такого файла нет в проекте, компиляция упадёт.
- Если изображение подготовлено — укажи путь до файла.
- Если его ещё нет — создай файл-заглушку с тем же именем (расширение должно совпадать с именем в команде `image(...)`), чтобы сборка была чистой. Тип и содержимое плейсхолдера — на усмотрение модели: подойдёт любой валидный для Typst формат (PNG, JPEG и т.п.). Отметь пользователю, что картинку нужно заменить.

Путь до изображений следует указывать относительно файла Typst, а не *pwd* команды компиляции.
Если проект имеет следующую структуру:

```
ProjectRoot/
├── img/
└── typst/
    └── report.typ
```

то путь до изображения пишется как `../img/<файл изображения>`.


## Запреты

- Не начинай работу над отчётом, не выполнив обязательную проверку окружения
  (см. «Обязательная проверка окружения»).
- Не пропускай обязательные пробельные строки (`\`) перед и после таблиц, рисунков и листингов кода, а также перед заголовками разделов/подразделов, когда слева от заголовка обычный текст. После заголовков разделов и подразделов (уровни 1-2) пробельную строку НЕ ставят — её добавляет стиль автоматически; после пунктов (уровень 3) пробельную строку не ставят никогда.
- Не выдумывай структуру титульного листа, содержания или приложений — опирайся на правила `formatting-rules/` и эталон.
- Не используй альтернативные пакеты для оформления отчётов по ГОСТ (только Ghost).
- Не изменяй эталонные файлы и локальные дополнения пакета Ghost без необходимости; при изменении делай бекап.

## Подробности

Полный справочник по стилю, локальным дополнениям пакета Ghost — в `resources/formatting-rules/README.md`.
