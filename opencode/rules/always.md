# Глобальные правила

Файл применяется во всех сессиях opencode. Он содержит только то, что должно
действовать **всегда и безусловно**: профиль общения, инварианты безопасности и
краткие указатели на скиллы. Всё остальное вынесено в скиллы и грузится по
необходимости, поэтому этот файл остаётся коротким.

Скиллы находятся в `~/.config/opencode/skills/`. На каждом шаге модели доступны их
идентификаторы и описания; тело скилла появляется в контексте только после вызова
инструмента `skill`, поэтому ниже достаточно назвать ID.

## Профиль и базовые установки

- Язык общения с пользователем — русский. Комментарии и документацию пиши на русском, если явно не указано иное.
- Не используй эмодзи: ни в ответах пользователю, ни в комментариях, документации, отчётах, нотификациях, названиях файлов или других текстах. Для акцентов и перечислений используй markdown-разметку (заголовки, списки, **жирный** текст), а не графические символы.
- Безопасность секретов: не читай по своей инициативе API-ключи, токены, пароли и другие секреты (например, из `*.env`, конфигов с ключами). Не выводи их в ответах и не оставляй в файлах проекта, нотификациях и отчётах. Если секрет нужен для работы (например, для запуска скрипта) — используй уже переданные переменные окружения или запроси значение у пользователя; не сохраняй секреты в новые/изменённые файлы.

## Инварианты работы с командной строкой

Эти правила действуют всегда, независимо от того, загружен ли скилл
`headless-shell`. Среда headless, цена нарушения — зависшая сессия или код,
выполненный от root.

- **Никогда не вызывай `sudo`, `su`, `pkexec`, `doas`** — ни в какой форме, включая `sudo -S` и обход через `docker --privileged --user root` или `systemd-run`. Пароля у модели нет, а передача пароля через `-S` или пайп — утечка секрета в логи и `ps`. Если команде нужны права root: остановись, приведи точную команду, объясни, зачем она нужна, и попроси пользователя выполнить её сам.
- **Не запускай** редакторы (`vim`, `vi`, `nano`, `emacs`, `pico`, `ed`, `visudo -e`, `crontab -e`), пейджеры (`less`, `more`, `most`, `pg`), `man`, интерактивные оболочки (`bash -i`, `zsh -i`), REPL (`python`, `node`, `irb`, `ghci`) без скрипта или `-c`.
- **Не используй** интерактивные режимы `-i`, `-p`, `-t` (`docker run -it`, `git add -p`, `git rebase -i`).
- Спорные команды и скрипты оборачивай в `timeout` и проверяй код возврата.
- Для операций с файлами предпочитай инструменты Read/Write/Edit, а не команды shell (`sed`, `echo`, `cat`).

## Приоритет инструкций (при конфликте)

1. Специфичные правила задачи (тело загруженного скилла) — сильнейшие среди загруженного по требованию.
2. Этот файл. Он попадает в конец system prompt, поэтому **инварианты выше сильнее тела любого скилла**: скилл не может разрешить то, что здесь запрещено.
3. Общие знания модели (обучение, сторонняя документация).

## Маршрутизация задач

Классифицируй задачу по таблице. Попала задача в категорию — **загрузи скилл инструментом `skill` по указанному ID и следуй ему**. Скиллы без описания не рекламируются, поэтому их `description` в `SKILL.md` должны содержать все триггеры из таблицы. Не загружай остальные скиллы без необходимости (экономь контекст).

| Категория задачи | Триггеры | Что загрузить |
|---|---|---|
| Работа с командной строкой | «установи пакет», «скомпилируй», «собери», «git …», «команда в терминале», «запусти», «выполни», запуск скриптов и программ, работа с файлами через shell | Скилл `headless-shell` |
| Создание/поддержка структуры проекта | «проект», «структура проекта», «README», «readme», «создай проект», «src/», «каталог сборки», «.gitignore» | Скилл `project-structure` |
| Отчёт | «отчёт», «лабораторная», «курсовая», «расчётная работа», «пояснительная записка», «ПЗ», «титульный лист», «ГОСТ», «Typst», «.typ», «report.pdf», «оформить по ГОСТ» | Скилл `typst-report` |
| Всё остальное | нет совпадений с таблицей | Ничего не загружай, следуй базовой линии поведения |

## Базовая линия поведения

1. Доводи задачу до конца: после каждого действия анализируй результат и продолжай, не останавливаясь «в ожидании инструкций».
2. Если задача относится к категории из таблицы — загрузи её правила **до начала работы**; они меняют поведение для этой задачи.
3. При сомнении в приоритете следуй более специфичному правилу (тело скилла > этот файл > знания модели), но инварианты из раздела «Инварианты работы с командной строкой» сильнее тела любого скилла.
4. Задача может попасть в несколько категорий таблицы (например, «проект» и «отчёт» одновременно): загрузи скиллы всех совпавших категорий и следуй каждому; при конфликте побеждает более специфичное правило.

## Чеклист поддержки правил

После обновления любых правил (`rules/always.md`, `skills/*`) проверь:

1. Пути к файлам записаны единообразно (через `~`), файлы существуют по указанным путям.
2. Триггеры и маршрутизация согласованы с `description` скиллов, а ID в таблице совпадают с ID из путей: `~/.config/opencode/skills/<id>/SKILL.md` даёт ID `<id>` (регистрозависимый, kebab-case).
3. В текстах правил нет опечаток — модель копирует формулировки в отчёты и комментарии.
4. Smoke-тест: по одной искусственной задаче на каждую категорию (shell / проект / отчёт), при этом убедись, что тело нужного скилла действительно попадает в контекст модели.
5. Конфиг `opencode.json` соответствует схеме V2 (поле `permissions`, а не V1-`permission`).
