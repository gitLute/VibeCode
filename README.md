# VibeCode — конфигурация OpenCode

Набор правил, скиллов и плагина для [OpenCode](https://opencode.ai), которые
превращают агента из «чата с файлами» в предсказуемого исполнителя: жёсткие
инварианты безопасности, готовые сценарии работы и оформление отчётов по ГОСТ.

Всё содержимое лежит в каталоге `opencode/` — это ровно то, что копируется в
`~/.config/opencode/`. Установка состоит из копирования каталога и одной
команды установки зависимостей.

## Что внутри

| Путь | Назначение |
|---|---|
| `opencode/rules/always.md` | Глобальные правила: профиль общения, запреты на `sudo`/REPL/пайгеры, таблица маршрутизации задач по скиллам и MCP-серверам. Подключается плагином, а не механизмом `instructions`, — см. ниже. |
| `opencode/skills/headless-shell/` | Безопасная работа с shell в headless-среде. Справочники `references/`: `cheatsheet.md` (неинтерактивные флаги), `hazards.md` (что зависает), `env.md` (работа с окружением). |
| `opencode/skills/project-structure/` | Каркас нового проекта (`src/`, `out/`, `img/`, `typst/`, `tmp/`, `README.md`) и скрипт `templates/scaffold.sh`, создающий его одной командой. |
| `opencode/skills/typst-report/` | Отчёты (лабораторные, курсовые, ПЗ) в Typst по ГОСТ. Правила оформления, эталоны для лабораторной и ПЗ, проверка окружения. |
| `opencode/plugins/global-instructions/` | Плагин на TypeScript: перед каждым запросом к модели дописывает `rules/always.md` в конец system prompt. |
| `opencode/opencode.json` | Основной конфиг: shell, плагин, права доступа, MCP. |
| `opencode/tui.json` | Настройки интерфейса: прокрутка, диффы, уведомления. |
| `opencode/package.json` | Зависимость `@opencode-ai/plugin` для плагина. |

### Почему правила подключены плагином

Файл `rules/always.md` большой, и opencode подставляет такие файлы в
*середину* system prompt, где их перебивают агентские инструкции, инструкции
MCP-серверов и описания скиллов. Плагин `global-instructions` через хук сессии
`context` добавляет те же правила в **конец** system prompt — с наивысшим
приоритетом. Без него правила формально загружены, но фактически проигрывают
соседним инструкциям.

Схема плагина (`export default { id, setup }`) подтверждена для **v2.0.8**.

## Требования

- **OpenCode v2.0.8** или новее. Плагин использует V2-формат, в v1.x не загрузится.
- **Bun или Node.js** с менеджером пакетов — для установки зависимости плагина.
- Bash как системный shell (в конфиге прописан `/bin/bash`).
- **Node.js 20+** — только если будете ставить MCP-серверы локально.

Необязательно:

- **Typst 0.13+** и пакет `@mih4n/ghost` — только для скилла `typst-report`.
  Требования и известная поломка пакета описаны в разделе
  [Скилл typst-report](#скилл-typst-report).

## Установка

### Вариант 1: вручную

```bash
git clone https://github.com/gitLute/VibeCode.git
cp -r VibeCode/opencode/. ~/.config/opencode/
cd ~/.config/opencode
npm install
opencode reload
```

Ничего подставлять и править не нужно: ни путей, ни токенов, ни имён
собственных каталогов. OpenCode сам находит плагин в каталоге `plugins/` рядом
с конфигом, а `opencode.json` не содержит ни одного машинно-зависимого пути.

`npm install` обязателен: без `@opencode-ai/plugin` из `node_modules` плагин не
загрузится, и правила перестанут действовать.

> **Внимание, если у вас уже есть `~/.config/opencode`.** Команда `cp`
> перезапишет `opencode.json`, `tui.json`, `rules/always.md` и
> `package.json`. Сделайте резервную копию и перенесите свои правки в новые
> файлы вручную:
>
> ```bash
> cp -r ~/.config/opencode ~/.config/opencode.bak
> ```
>
> Свои MCP-серверы, провайдеры и правила доступа из старого `opencode.json`
> нужно положить в новый вручную: `opencode.json` в репозитории содержит
> только универсальную часть, без личных серверов и токенов.

### Вариант 2: поручить агенту

Дайте агенту OpenCode этот промпт:

```
Установи мне конфигурацию из репозитория
https://github.com/gitLute/VibeCode.git.
Следуй инструкции в README, раздел «Установка: для агента».
```

Или, если агент уже работает с этим репозиторием локально:

```
Установи мне конфигурацию из этого репозитория.
Следуй инструкции в README, раздел «Установка: для агента».
```

## Установка: для агента

Инструкция для агента OpenCode. Выполняй шаги строго по порядку и не переходи
к следующему, пока текущий не вернул ожидаемый результат.

### Шаг 0. Определи целевой каталог

Целевой каталог конфигурации:

```bash
opencode debug paths
```

В строке `config` указан путь, который нужно заполнить (у пользователя это
`~/.config/opencode`). **Не хардкодь этот путь** — возьми его из вывода
команды, он зависит от `XDG_CONFIG_HOME`. Если `XDG_CONFIG_HOME` задан,
используй `$XDG_CONFIG_HOME/opencode`.

### Шаг 1. Проверь версию OpenCode

```bash
opencode --version
```

Требуется **2.0.8 или новее**. Если ниже — остановись и сообщи пользователю:
плагин `global-instructions` написан под V2 и в v1.x не загрузится.

### Шаг 2. Сделай резервную копию

Выполняй, только если целевой каталог уже существует и не пуст:

```bash
[ -d "$CONFIG_DIR" ] && cp -r "$CONFIG_DIR" "$CONFIG_DIR.bak.$(date +%Y%m%d-%H%M%S)"
```

Если нужны права на запись в каталог — **не вызывай `sudo`**. Остановись,
покажи пользователю точную команду и попроси выполнить её сам.

### Шаг 3. Скопируй файлы

Копируй содержимое каталога `opencode/` из репозитория в целевой каталог:

```bash
cp -r /path/to/VibeCode/opencode/. "$CONFIG_DIR/"
```

`cp -r .../opencode/.` с точкой на конце копирует и скрытые файлы, включая
`.gitignore`.

### Шаг 4. Установи зависимости плагина

```bash
cd "$CONFIG_DIR" && npm install
```

Проверь результат: каталог `$CONFIG_DIR/node_modules/@opencode-ai/plugin`
должен существовать. Если нет — сообщи пользователю, дальше не иди.

Ничего подставлять в `opencode.json` не нужно: OpenCode сам находит плагин в
каталоге `plugins/` рядом с конфигом, путь в конфиге не указывается.

### Шаг 5. Проверь, что плагин загрузился

Проверяй по логу, а не по `opencode plugin list`: подкоманда отдаёт результат
из фонового сервиса и может показать `No plugins found` даже при полностью
рабочей конфигурации. Лог — единственный надёжный источник.

```bash
LOGDIR="$(opencode debug paths | awk '$1=="log"{print $2}')"
grep -c "loading plugin" "$LOGDIR"/*.log
grep "failed to load plugin" "$LOGDIR"/*.log
```

Правильный результат:

- `loading plugin` — ненулевое число вхождений, в строке есть
  `global-instructions`;
- `failed to load plugin` — **ни одного** вхождения (пустой вывод).

Если есть `failed to load plugin`, покажи пользователю строку из лога, не
пытайся чинить наугад.

### Шаг 6. Проверь, что конфиг читается

```bash
opencode debug config
```

В выводе должен быть документ с путём к твоему `opencode.json` и ключами
`permissions` и `shell`.

### Шаг 7. Перезагрузи конфигурацию

```bash
opencode reload
```

Внутри уже запущенной сессии конфиг перечитается. Если команда недоступна —
попроси пользователя перезапустить opencode.

### Шаг 8. Отчитайся

Сообщи пользователю:

- путь, куда установлено;
- версию opencode (`opencode --version`) и результат проверки плагина из шага 5;
- путь к резервной копии, если она была сделана;
- какие файлы требуют ручной правки: см. раздел «Что настроить под себя»;
- предупреждение про MCP-серверы из раздела «Важно про MCP-серверы».

### Запреты

- Не вызывай `sudo`, `su`, `pkexec` — только попроси пользователя.
- Не редактируй и не удаляй `rules/always.md` и содержимое `skills/`, если
  пользователь не попросил. Это ядро конфигурации, а не настройка.
- Не вписывай токены прямо в `opencode.json`. Только ссылкой
  `{file:~/.config/opencode/.secrets/<имя>}`.
- Не создавай `~/.config/opencode/.secrets/` содержимым из репозитория.
- Не запускай интерактивные команды: редакторы, пайджеры, `man`, REPL без
  скрипта, флаги `-i`, `-p`, `-t`. Агент работает в headless-среде, такая
  команда зависнет до таймаута.
- Не запускай `opencode` в интерактивном TUI — только перечисленные выше
  неинтерактивные подкоманды.

## Что настроить под себя

Установленный конфиг рабочий, но универсальный. Разбор по пунктам.

### `opencode.json`

| Что | Зачем |
|---|---|
| `permissions` | Правила доступа. Порядок важен: правила проверяются по порядку, первое совпадение решает. Правило `deny` на внешний каталог ставь **после** `allow` на его родителя, иначе `allow` его перебьёт. |
| `mcp.servers` | По умолчанию секции нет — примеры в комментариях. Добавляй нужные серверы. |
| `shell` | Если у тебя другой путь к bash, поправь. |
| `compaction.buffer` | Запас контекста под сворачивание длинной сессии. |

Плагин в `opencode.json` не прописан — он находится автоматически по пути
`plugins/global-instructions/index.ts`. Если захочешь подключить плагин из
другого места, поле `plugins` для этого есть, но не указывай в нём `~`:
opencode может не развернуть его и истолковать запись как имя npm-пакета,
после чего плагин молча не загрузится.

### Запрет на чтение изображений

В конфиге стоит `deny` на `read` для `*.png`, `*.jpg`, `*.jpeg`, `*.gif`,
`*.webp`, `*.svg` и их вариантов в верхнем регистре. Смысл: картинки дорого
стоят по токенам и почти не нужны агенту для работы с кодом. Список сокращён
до основных форматов — при необходимости допиши свои (RAW-форматы камер,
`*.avif`, `*.heic`, `*.jxl`).

Если изображения нужны (например, агент смотрит скриншоты вёрстки) — удали эти
правила, иначе `read` вернёт отказ.

### Секреты

Токены хранятся отдельными файлами и подставляются ссылкой, а не текстом:

```json
"headers": {
  "Authorization": "Bearer {file:~/.config/opencode/.secrets/context7}"
}
```

Создай каталог `~/.config/opencode/.secrets/`, положи в него файлы с токенами и
выставь права `600`. Правила в `opencode.json` запрещают агенту и читать, и
запускать команды, затрагивающие `.secrets`, и сам каталог не попадает в git.

### `tui.json`

Косметика интерфейса: скорость прокрутки, показ диффов, звук и уведомления об
окончании ответа. Меняй под вкус, ничего не сломается.

### `rules/always.md`

Файл на русском и задаёт профиль общения: русский язык, запрет эмодзи,
таблица маршрутизации задач по скиллам. Перед правкой прочитай его целиком —
это короткий, но связный документ. Правь его в своём `~/.config/opencode`, а не
в форке репозитория: он не переживёт `git pull`.

Согласованность важнее: если переименовал скилл в таблице маршрутизации —
переименуй и каталог, иначе модель будет грузить несуществующий скилл.

## Важно про MCP-серверы

`opencode.json` в репозитории содержит **только универсальную часть**: личные
MCP-серверы автора (расписание университета, скриншоты Wayland, локальный
провайдер) вырезаны, потому что содержат абсолютные пути и токены.

Но в `rules/always.md` остались строки таблицы маршрутизации про эти серверы.
Если установишь конфиг как есть, модель получит инструкцию использовать
`gstu-schedule` и `wayland-shot`, которых в системе нет.

Что делать:

- установи нужные MCP-серверы и опиши их в секции `mcp.servers`; или
- удали соответствующие строки из таблицы в `rules/always.md`, если серверы
  тебе не нужны.

Опция «ничего не делать» тоже работает: агент попробует вызвать несуществующий
сервер, получит ошибку и продолжит работу. Но лишний шум в сессии.

## Скилл typst-report

Скилл оформляет отчёты по ГОСТ в Typst поверх пакета `@mih4n/ghost:1.0.1`.
Без установленного Typst остальные скиллы работают нормально.

Проверка окружения (её же выполняет агент автоматически):

```bash
typst --version
cd ~/.config/opencode/skills/typst-report/resources
typst compile --root . env-check.typ /tmp/env-check.pdf
```

`env-check.typ` импортирует пакет, применяет стиль `styles.extended` и вызывает
все титульные страницы, таблицу, рисунок и приложения. Смысл: поймать не только
отсутствие пакета, но и поломку его внутренних импортов.

**Известная проблема пакета 1.0.1.** После `typst update` пакет из
`gitLute/GhostExtended` ломается: его `pages/index.typ` и `styles/index.typ`
ссылаются на удалённые локальные файлы, из-за чего падает **любой** импорт
пакета, включая импорт стиля. Точные правки перечислены в
`skills/typst-report/resources/formatting-rules/01-import-style.md`; перед
изменением делай бекап файлов пакета.

Агент по инструкции скилла чинит пакет, а не подменяет его другим пакетом ГОСТ
и не переписывает отчёт под сломанный пакет.

Эталоны готовых работ лежат в `resources/lab-style/` (лабораторная, расчётная,
курсовая) и `resources/curse-style/` (пояснительная записка).

## Проверка после установки

```bash
opencode debug paths    # config указывает на твой каталог
opencode debug config   # документ с путём к opencode.json, ключи permissions и shell

LOGDIR="$(opencode debug paths | awk '$1=="log"{print $2}')"
grep -c "loading plugin" "$LOGDIR"/*.log              # больше нуля, есть global-instructions
grep "failed to load plugin" "$LOGDIR"/*.log          # пусто
```

Не полагайся на `opencode plugin list`: он читает состояние фонового сервиса и
может показать `No plugins found` при полностью рабочей конфигурации. Лог
надёжнее.

Функциональная проверка — новая сессия и вопрос, который требует правил,
например «установи пакет через pip». В ответе агент должен сослаться на
скилл `headless-shell`, а не предложить запустить REPL. Если не сослался —
правила не доходят, вернись к шагу 5.

## Удаление

```bash
rm -rf  ~/.config/opencode/{rules,skills,plugins}
rm -f   ~/.config/opencode/{opencode.json,tui.json,package.json,package-lock.json}
rm -rf  ~/.config/opencode/node_modules
```

Резервная копия из шага 2 лежит рядом с каталогом конфигурации
(`~/.config/opencode.bak.<метка>`) и удалением не затрагивается. Полное
отключение — вернуть её на место.

Каталог `.secrets/` в удалении не участвует: там лежат твои собственные токены,
их нужно убрать руками.
